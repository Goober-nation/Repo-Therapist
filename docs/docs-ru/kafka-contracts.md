# Контракты сообщений Kafka

Область: формы сообщений, публикуемых и потребляемых на связях Kafka из схемы архитектуры:

- Aggregator ↔ Grade service — топики `grading.requests` / `grading.results`, **описаны ниже**.
- Grade service ↔ Repository service — **описано ниже**. Этот обмен целиком в зоне одного
  человека (Repository + Grade service), поэтому не требовал общего согласования команды.
- Grade service ↔ LLM service — **описано ниже как плоские сообщения `repo.docs.*`** для анализа
  документации.
- Aggregator ↔ LLM service — **описано ниже как плоские сообщения `llm.recommendations.*`** для
  сводки по репозиторию и приоритизированных рекомендаций (заменяет конверт отчёта v2).
- Grade service ↔ Security wrapper — не через Kafka: Grade service вызывает обёртку напрямую по
  gRPC (`GetAppsecResult`), см. `grading/security.md`.

> **Примечание к переводу (проверено по коду, 2026-09-28).** В английском оригинале в начале
> списка остались устаревшие пункты «ещё не определено» для Aggregator ↔ Grade, Grade ↔ Security
> и Grade ↔ LLM; в переводе они заменены актуальным состоянием. Поля `repo.ready` исправлены по
> `internal/contracts/repo_grading.go`.

## Переменные окружения топиков (2026-09-28)

Каждое имя топика ниже — значение по умолчанию. Все сервисы читают одну и ту же переменную для
его переопределения, так что одно значение переименовывает топик везде; если ничего не задавать,
остаются документированные имена.

| Топик (по умолчанию) | Переменная | Какие сервисы читают |
|---|---|---|
| `grading.requests` | `KAFKA_GRADING_REQUESTS_TOPIC` | aggregator, grade |
| `grading.results` | `KAFKA_GRADING_RESULTS_TOPIC` | aggregator, grade |
| `repo.grade.requested` | `KAFKA_REPO_GRADE_REQUESTED_TOPIC` | grade, repository |
| `repo.ready` | `KAFKA_REPO_READY_TOPIC` | grade, repository |
| `repo.docs.grade.requested` | `KAFKA_DOCS_GRADE_REQUESTED_TOPIC` | grade, llm |
| `repo.docs.graded` | `KAFKA_DOCS_GRADED_TOPIC` | grade, llm |
| `llm.recommendations.requested` | `KAFKA_LLM_REQUESTS_TOPIC` | aggregator, llm |
| `llm.recommendations.received` | `KAFKA_LLM_RECOMMENDATIONS_TOPIC` | aggregator, llm |

LLM-сервис по-прежнему принимает старые `LLM_SUMMARY_REQUEST_TOPIC`/`LLM_SUMMARY_RESULT_TOPIC`
как запасные; если заданы обе, побеждает переменная `KAFKA_*`.

## `repo.grade.requested`

Производитель: Grade service, ретранслирующий каждое сообщение `grading.requests` от Aggregator
(или от ручной команды `grading-request`). Потребитель: Repository service.

```json
{
  "org_slug": "examples",
  "repo_slug": "vulnerable-repo",
  "requested_at": "2026-09-19T23:49:12+03:00",
  "token": "<необязательный PAT SourceCraft пользователя>"
}
```

Собственные топики Aggregator в том виде, как их читает/пишет Grade service:

- `grading.requests`: `{org_slug, repo_slug, visibility, requested_at, token?}`. Токен означает
  приватное оценивание; без токена — публичное. Непубличный `visibility` без токена отбрасывается.
- `grading.results`: `{sourcecraft_uuid, visibility, score, category_scores, advice,
  missing_data, graded_at, error}`. `visibility` называет таблицу оценок, в которую пишет
  Aggregator. `advice` — список не более чем из `GRADE_ADVICE_LIMIT` (по умолчанию 0 = все)
  рекомендаций `{category_id, metric_id, text}`, выбранных случайно. Для документации это тексты
  `advice` из `repo.docs.graded`, каждый как `{"documentation", "llm_advice", "[medium] <текст>"}`. `error` при успехе — `""`.
  При сбое это код — `REPO_FETCH_FAILED` (repo.ready со статусом failed), `GRADING_FAILED`,
  `GRADING_INTERRUPTED` (grade-service остановлен посреди оценки), `RESULT_BUILD_FAILED` — а
  `score`, `category_scores` и `advice` равны null; Aggregator тогда снимает блокировку
  репозитория и один раз сообщает о сбое следующему запросу оценки этого репозитория. Сбой без
  `sourcecraft_uuid` нельзя сопоставить, и он не публикуется; такую блокировку Aggregator
  снимает сам, когда она занята дольше `GRADING_LOCK_TIMEOUT` (по умолчанию 20m).

`token` копируется из `grading.requests`. Если он есть, Repository service использует его для
вызовов обёртки и git clone; если нет — свой `SOURCECRAFT_PAT`. Токен никогда не логируется и
намеренно **не** повторяется в `repo.ready` — Grade service хранит его в памяти (по ключу
`org/repo`, удаляется при `repo.ready` или через 30 минут) для собственного вызова Security
wrapper.

## `repo.ready`

Производитель: Repository service, после завершения (успешного или нет) обработки сообщения
`repo.grade.requested`. Потребитель: Grade service.

```json
{
  "org_slug": "examples",
  "repo_slug": "vulnerable-repo",
  "sourcecraft_uuid": "019b2102-fa21-7ab7-8ce1-116af406fb5e",
  "s3_prefix": "repos/019b2102-fa21-7ab7-8ce1-116af406fb5e",
  "status": "ready",
  "commit_count": 3,
  "issue_count": 2,
  "milestone_count": 0,
  "ready_at": "2026-09-19T23:49:15+03:00"
}
```

`status` — `"ready"` или `"failed"`; при сбое `error` содержит сообщение, а поля счётчиков
опускаются (они `omitempty`, поэтому нулевые счётчики тоже не передаются). Grade service
логирует и пропускает сообщения `"failed"`, не пытаясь их оценить.

Go-типы: `internal/contracts/repo_grading.go`. Проверено сквозным прогоном (2026-09-19): ручной
запуск → Repository service → `repo.ready` → Grade service → напечатанная оценка «Активности»,
совпавшая с результатом, ранее независимо проверенным вручную.

# Контракты LLM-сервиса (версионируемые)

Эти контракты добавляют два независимых асинхронных процесса. Они не меняют существующие сообщения
`repo.grade.requested` и `repo.ready`.

1. Grade service отправляет S3-префикс репозитория и получает итоговую нормированную оценку
   документации, оценки её восьми разделов и рекомендации по недостаткам. LLM-сервис владеет
   методикой оценки документации; Grade service — межкатегорийной агрегацией и итоговым Repo
   Health Score.
2. Aggregator запрашивает русскоязычную сводку и рекомендации, когда все оценки окончательны.
   LLM-сервис не пересчитывает и не меняет эти оценки.

Содержимое репозитория никогда не кладётся в сообщения Kafka. Запросы документации содержат
S3-префикс из `repo.ready`, а не файлы репозитория. Запросы сводки содержат только итоговые оценки
и рекомендации; при генерации файлы репозитория повторно не читаются.

## Граница LLM-сервиса

Документация и лучшие практики — единственная категория, которую оценивает LLM-сервис. В ней
обычный код выполняет объективные проверки, а модель — смысловые. LLM-сервис объединяет обе части
по версионированной методике и возвращает итоговую нормированную оценку документации и оценки
разделов. Grade service принимает эту оценку категории, не пересчитывая её внутренние проверки.
Ответ по документации содержит в `advice` только шаблонные рекомендации на русском — без причин,
ссылок на файлы и дополнительного вызова модели. Отдельная сводка Aggregator может дать более
широкое объяснение.

Активность, Безопасность, CI/CD, Задачи и Здоровье кода оцениваются алгоритмически вне
LLM-сервиса. LLM-сервис не читает их сырые данные, не запускает их анализаторы и не считает их
оценки. Их итоговые оценки он видит только в `llm.recommendations.requested`, где они являются
неизменяемым исходным материалом для текста, понятного человеку.

## Топики и владельцы

| Топик | Производитель | Потребитель | Ключ сообщения Kafka |
|---|---|---|---|
| `repo.docs.grade.requested` | Grade service | LLM service | `sourcecraft_uuid` |
| `repo.docs.graded` | LLM service | Grade service | `sourcecraft_uuid` |
| `llm.recommendations.requested` | Aggregator | LLM service | `sourcecraft_uuid` |
| `llm.recommendations.received` | LLM service | Aggregator | `sourcecraft_uuid` |
| `llm.report.requests` | *(заменён, не реализован)* | | `analysis_id` |
| `llm.report.results` | *(заменён, не реализован)* | | `analysis_id` |

Все экземпляры LLM-сервиса, обрабатывающие документацию, используют одну группу потребителей;
обработчики рекомендаций — другую общую группу. Значения по умолчанию в коде:
`llm-service-documentation-v1` (переопределяется `LLM_KAFKA_GROUP_ID`) и
`llm-service-recommendations-v1` (переопределяется `LLM_SUMMARY_KAFKA_GROUP_ID`). Разные
логические потребители не должны делить одну группу: участники группы делят сообщения, а не
получают каждый по копии.

Производители должны использовать партиционер с учётом ключа из таблицы выше, чтобы сообщения с
одинаковым ключом попадали в одну партицию топика. Kafka гарантирует порядок только внутри одной
партиции топика; ни один процесс не может полагаться на порядок между разными топиками.

## Конверт событий отчёта (не используется для оценки документации)

События отчёта — JSON в UTF-8 с таким предложенным конвертом:

```json
{
  "event_id": "018f47d2-6d5a-7b72-82fd-1e9834d57a91",
  "event_type": "documentation.analysis.requested",
  "event_version": 1,
  "analysis_id": "018f47d1-e33b-7af3-a642-229ac22a9e82",
  "repository_id": "019b2102-fa21-7ab7-8ce1-116af406fb5e",
  "data_scope": "public",
  "created_at": "2026-09-21T10:15:30Z",
  "payload": {}
}
```

Поля конверта:

| Поле | Значение |
|---|---|
| `event_id` | UUID этого события Kafka. Повтор того же логического события сохраняет этот ID. |
| `event_type` | Один из шести типов событий, определённых ниже. |
| `event_version` | Версия контракта для этого типа события; неподдерживаемые версии явно отвергаются. |
| `analysis_id` | UUID одного полного прогона анализа репозитория. Используется как ключ Kafka. |
| `repository_id` | UUID репозитория SourceCraft. Slug-и — метаданные для отображения, а не идентичность. |
| `commit_sha` | Полный SHA коммита Git, если он известен производителю. Текущий обмен `repo.ready` между Repository и Grade его не передаёт, поэтому для событий документации поле необязательно. |
| `data_scope` | `public` для только публичных данных или `owner` для данных, доступных авторизованному владельцу. |
| `created_at` | Метка времени RFC 3339 в UTC. Производители выдают форму с `Z`. |
| `payload` | Объект, специфичный для события. |

Текущие версии: запрос/сбой документации = 1; завершение документации = 2; запрос/завершение
отчёта = 2; сбой отчёта = 1 (конверт ошибки не изменился). Python-парсер запросов на время
миграции принимает и устаревший запрос отчёта v1. Отчёт v1 сохраняет прежние правила влияния
проблем; новые производители используют v2 для компактных фактов документации.

События результата и сбоя дополнительно требуют `request_event_id`, равный `event_id` запроса,
на который они отвечают. Они без изменений копируют из запроса `analysis_id`, `repository_id`,
`data_scope` и `commit_sha` (если есть).

Aggregator создаёт `analysis_id` при старте полного прогона анализа, и каждый сервис передаёт его
без изменений. Производитель каждого события создаёт его `event_id`; поэтому LLM-сервис создаёт
новый `event_id` для своего завершающего ответа, сохраняя ID запроса в `request_event_id`.

Никакое событие не может содержать учётные данные, токены SourceCraft/Yandex, секретные ключи S3,
полные промпты или целые файлы репозитория. Сериализованное событие должно быть меньше 512 КиБ,
чтобы с запасом укладываться в обычный лимит записи Kafka 1 МиБ.

## Оценка документации: активный контракт Grade ↔ LLM

Активный обработчик использует плоские JSON-объекты без конверта и полей версии. Оба топика
используют `sourcecraft_uuid` как ключ Kafka.

Grade → LLM, топик `repo.docs.grade.requested`:

```json
{
  "sourcecraft_uuid": "019b2102-fa21-7ab7-8ce1-116af406fb5e",
  "s3_prefix": "repos/019b2102-fa21-7ab7-8ce1-116af406fb5e",
  "requested_at": "2026-09-26T12:00:00Z"
}
```

LLM → Grade, топик `repo.docs.graded` (успешная оценка):

```json
{
  "sourcecraft_uuid": "019b2102-fa21-7ab7-8ce1-116af406fb5e",
  "grade": 85,
  "subgrades": {"required_files": 100, "purpose": 80, "local_run": 75},
  "advice": ["Уточните, какую задачу решает проект, для чего его используют и какой результат он даёт."],
  "error": "",
  "evaluated_at": "2026-09-26T12:00:10Z"
}
```

LLM → Grade, тот же топик и ключ Kafka (оценка не удалась):

```json
{
  "sourcecraft_uuid": "019b2102-fa21-7ab7-8ce1-116af406fb5e",
  "grade": null,
  "subgrades": {},
  "advice": [],
  "error": "CONTENT_FILTER",
  "evaluated_at": "2026-09-26T12:00:10Z"
}
```

`error` — всегда строка. Пустая строка означает успешную оценку; Grade использует `grade` и
`subgrades`. Любая непустая строка означает сбой; Grade помечает документацию как `NO_DATA` и
игнорирует все поля оценки. Строка — короткий стабильный код ошибки без секретов и сырого
содержимого модели/репозитория. При сбое `grade` равен `null`, `subgrades` — `{}`, `advice` —
`[]`; ноль никогда не обозначает недоступную оценку. `evaluated_at` фиксирует момент завершения
попытки, успешной или нет. Оба исхода используют исходный `sourcecraft_uuid` как поле сообщения и
ключ Kafka.

Ключи разделов: `required_files`, `purpose`, `local_run`, `build`, `testing`, `usage`,
`structure`, `consistency`. Непросмотренные или неприменимые разделы опускаются в `subgrades` и
никогда не заменяются нулём или null. Итог нормируется по оценённым проверкам до округления; это
не среднее арифметическое процентов разделов. Успешные оценки на проводе — целые 0–100,
округление половины вверх. `advice` содержит только рекомендации по улучшению в виде строк на
русском, выбранные по коду недостатка, с запасным вариантом на уровне раздела для неизвестных
кодов. Причины, имена файлов, доказательства и хэши в `advice` не включаются. Непросмотренные/
неприменимые разделы и разделы с идеальной оценкой рекомендаций не дают. Внутренние
структурированные факты и оценки сохраняются; дополнительный вызов модели не делается.
Метки времени — RFC3339 с часовым поясом. S3-префикс — относительный префикс ключа объекта без
завершающего слэша. Сервис только читает объекты репозитория.

Обработчик фиксирует смещение входного сообщения только после того, как Kafka подтвердит
соответствующий результат успеха или сбоя. Отказ фильтра содержимого или исчерпанные попытки
модели/S3 дают результат сбоя, если у запроса корректный `sourcecraft_uuid`. Если истекает
60-секундный бюджет вызова модели, код сбоя — `LLM_TIMEOUT`. Grade service сохраняет 70-секундный
запасной таймаут на случай отсутствия обработчика или сбоя брокера. Если не удалась сама
публикация результата, обработчик не может сообщить об этом через тот же топик и должен оставить
вход незафиксированным; запасным остаётся таймаут Grade. Некорректный запрос без надёжного UUID не
может дать сопоставимый результат и требует отдельной эксплуатационной обработки. Доставка «хотя
бы один раз»: падение между публикацией и фиксацией смещения может повторить результат. В этом
минимальном контракте нет ID запроса, поэтому параллельные прогоны оценки одного репозитория
нельзя надёжно сопоставить; потребители должны учитывать повторные результаты. Сервис не
заявляет обработку «ровно один раз».

Этот раздел определяет согласованный формат. Python-обработчик LLM выдаёт оба исхода;
Go-потребитель Grade считает непустой `error` или `grade: null` немедленным `NO_DATA` для
документации.

Старые конверты `documentation.analysis.*` — только устаревшие вспомогательные функции, активным
обработчиком Kafka не используются. Конверт отчёта ниже — отдельный предложенный интерфейс;
генерация отчёта этим обработчиком не реализована.

## Сводка и рекомендации по репозиторию: активный контракт Aggregator ↔ LLM (2026-09-27)

Плоский JSON без конверта. Оба топика используют `sourcecraft_uuid` как ключ Kafka. Имена топиков
переопределяются (см. «Переменные окружения топиков»); группа потребителей
(`llm-service-recommendations-v1`) — через `LLM_SUMMARY_KAFKA_GROUP_ID`.

Aggregator → LLM, топик `llm.recommendations.requested` (Go `LLMRecommendationsRequestedEvent`):

```json
{
  "visibility": "private",
  "sourcecraft_uuid": "019b2102-fa21-7ab7-8ce1-116af406fb5e",
  "org_slug": "examples",
  "repo_slug": "demo",
  "grade": {
    "Score": 64,
    "CategoryScores": {"security": 40, "activity": 90, "documentation": 70,
                       "ci_cd": null, "issues": 80, "code_health": 55},
    "Advice": ["Обновите уязвимые зависимости."],
    "MissingData": ["ci_cd"],
    "GradedAt": "2026-09-27T11:59:00Z"
  },
  "requested_at": "2026-09-27T12:00:00+03:00"
}
```

`grade` — это Go-структура `RepoGrade`, у которой есть только теги `db`, поэтому её поля приходят
с Go-именами. Парсер принимает и Go-имена (`Score`, `CategoryScores`, …), и snake_case (`score`,
`category_scores`, …); одно и то же поле в обоих написаниях отвергается. Правила:

- `visibility` — `public` или `private`; slug-и непустые; `requested_at` — RFC3339 (точность до
  наносекунд из Go принимается).
- `Score` — целое 0–100 или `null`. `CategoryScores` сопоставляет ID категории с числом 0–100,
  `null` (нет данных) или объектом с полем `score`. `Advice` и `MissingData` — списки строк или
  `null`. Остальные поля `grade` игнорируются.
- Для `public` категории `security` и `ci_cd` скрываются от модели, даже если присутствуют.

LLM → Aggregator, топик `llm.recommendations.received` (Go `LLMRecommendationsReceivedEvent`):

```json
{
  "sourcecraft_uuid": "019b2102-fa21-7ab7-8ce1-116af406fb5e",
  "raw_response": {
    "summary": "Репозиторий получил 64 балла из 100. …",
    "strengths": ["Активность проекта: 90/100", "Issues: 80/100"],
    "weaknesses": ["Безопасность (Security): 40/100", "Документация: 70/100"],
    "recommendations": [
      {"priority": "HIGH", "category": "security", "text": "Обновите уязвимые зависимости."}
    ]
  },
  "model_used": "aliceai-llm",
  "evaluated_at": "2026-09-27T12:00:08Z",
  "visibility": "private",
  "error": ""
}
```

Правила `raw_response`. Модель пишет только `summary` и тексты рекомендаций; всё остальное код
выводит из оценок запроса, поэтому оно полно и воспроизводимо:

- `summary` (модель): непустой текст на русском, не более 1500 символов.
- `strengths`, `weaknesses` (код): каждая категория с числовой оценкой, видимая для этого
  `visibility`, появляется ровно один раз как `"<название>: <оценка>/100"` — оценка 75 и выше в
  `strengths` (сначала наибольшие), ниже 75 в `weaknesses` (сначала наименьшие). Категории без
  данных не появляются никогда. Любой список может быть пустым.
- `recommendations`: до 8 объектов `{priority, category, text}`. Модель пишет `text` (не более
  600 символов) и выбирает `category` — всегда категорию с числовой оценкой, видимую для этого
  `visibility`. `priority` задаёт код по оценке этой категории: `HIGH` ниже 50 или безопасность
  ниже 75; `MEDIUM` ниже 75; иначе `LOW`. Сортировка по приоритету, затем по более слабой
  категории. Модель просят дать хотя бы одну рекомендацию на каждую слабую категорию; это не
  проверяется принудительно.
- Граница 75 выше (strengths/weaknesses, `MEDIUM`/`LOW` и `HIGH` для безопасности) —
  `LLM_STRENGTH_THRESHOLD` (целое 0–100, по умолчанию 75); граница 50 для `HIGH` фиксирована.
- Лишние маркеры списков и пунктуация по краям текста модели обрезаются. Формулировки не
  проверяются. Модели предписано использовать только данные запроса, не выдумывать цифры и факты
  и не считать отсутствие данных проблемой. Оценки она никогда не меняет.

При сбое `raw_response` равен `null`, а `error` — стабильный код: `INVALID_EVENT`, `NO_DATA` (ни
у одной категории нет оценки, модель не вызывается), `LLM_TIMEOUT`, `LLM_RATE_LIMITED`,
`LLM_PROVIDER_UNAVAILABLE`, `LLM_INVALID_RESPONSE`, `CONTENT_FILTER`, `INTERNAL_ERROR`.
`model_used` заполняется в обоих случаях. `visibility` копируется из запроса или равен `""`, если
в запросе не было корректного значения. Запрос без корректного `sourcecraft_uuid` нельзя
сопоставить: он логируется и пропускается.

В пределах 60-секундного бюджета модели разрешён один повтор для исправления формата. Смещение
входа фиксируется только после подтверждения результата Kafka. Доставка «хотя бы один раз»,
поэтому возможен повторный результат для того же `sourcecraft_uuid`.

### `report.generation.requested`

Топик: `llm.report.requests`.

Aggregator публикует это событие только после того, как Grade service и все анализаторы выдали
итоговые результаты. Факты документации передаются без изменений в `payload.documentation`; это
проверенные по формату утверждения модели, а не проверенные проблемы. `problems` содержит только
остальные категории. В запросе нет S3-снимка, потому что генерация отчёта должна использовать
итоговые факты, а не заново читать исходный код репозитория. В запросе отчёта v2 поле
`output_language` обязательно, и единственное поддерживаемое значение — `ru`.

Правила оценок:

- статус — одно из `CALCULATED`, `CALCULATED_PARTIAL`, `NO_DATA`, `NOT_CALCULATED` или `FAILED`;
- `score` — число от 0 до 100 для `CALCULATED` и `CALCULATED_PARTIAL`; иначе `null`;
- частично вычисленная категория содержит `coverage_percent`; полные результаты могут содержать
  его для единообразия;
- LLM-сервис сохраняет каждую переданную оценку в точности и никогда не выводит замену;
- присутствуют все шесть категорий, включая недоступные, чтобы отсутствие данных не могло
  исчезнуть из отчёта;
- `data_scope` определяет, какие проблемы может включить Aggregator. LLM-сервис не смешивает
  публичные и доступные только владельцу данные.

или `null`, если категория не удалась/недоступна. Сохраняйте её оценку, оценки разделов и все
ID/содержимое фактов. Оценка категории в `scores.categories` берётся из её `grade`. Фактам
документации не нужны важность, влияние на оценку или обязательные проверенные доказательства.

Правила проблем и вычетов для остальных пяти категорий:

- `id` уникален в пределах анализа и стабилен для переданного результата;
- `category` — одно из `security`, `activity`, `ci_cd`, `issues`, `code_health`; записи
  документации относятся только к `documentation.facts`;
- `severity` — `CRITICAL`, `HIGH`, `MEDIUM` или `LOW`; мелкие вычеты — `LOW`, а не опускаются;
- `score_impact.category_points_lost` — положительное число по шкале 0–100 этой категории;
- для каждой категории `CALCULATED` или `CALCULATED_PARTIAL` ниже 100 требуется хотя бы одна
  проблема этой категории;
- для каждой категории `CALCULATED` или `CALCULATED_PARTIAL` сумма вычетов её проблем равна
  `100 - score` (с точностью 0.01 на десятичное округление). У категории со 100 проблем нет;
- `code` и `facts` — машиночитаемые входные данные. Производители не готовят заранее заголовок,
  пояснение или рекомендацию;
- `code` выбирает версионированную схему фактов конкретной категории; неизвестные коды —
  некорректный ввод;
- доказательства передают и проверяют анализаторы, а не выдумывает модель отчёта;
- доказательство может ссылаться на файл, метрику, проблему AppSec, запуск CI, задачу, коммит,
  merge request или релиз. У каждого доказательства есть короткое проверенное `summary` и
  идентификаторы, нужные UI;
- весь запрос должен быть меньше 512 КиБ. При необходимости производители объединяют повторяющиеся
  сырые случаи в одну проблему со счётчиками/доказательствами, но ни одна причина вычета баллов не
  может быть опущена.

- `{"source_type":"documentation_fact","source_id":"<ID элемента documentation.facts>"}`;
- `{"source_type":"category_score","source_id":"<ID существующей категории>"}`;

выходного массива `problems`, чтобы даже мелкий вычет оставался видимым. Источники рекомендации
должны включать хотя бы одну проблему или факт документации. Точные прогнозы изменения общей
оценки не генерируются, потому что только Grade service может вычислять межкатегорийные и итоговые
изменения. LLM-сервис владеет только вычислением категории «Документация».
`category_assessments` содержит каждую категорию со статусом `CALCULATED` или
`CALCULATED_PARTIAL` ровно один раз, включая категории со 100. Оценка на 100 может только назвать
оценку; она не должна выдумывать подробную сильную сторону, которой не было в запросе.
`missing_data` содержит каждую категорию со входным статусом `NO_DATA`, `NOT_CALCULATED` или
`FAILED`, плюс замечание о покрытии для каждой категории `CALCULATED_PARTIAL`. Полностью
`CALCULATED` категорий в нём нет.

Контракт намеренно возвращает структурированное содержимое отчёта, а не Markdown или PDF. Слой
представления может отрисовать то же проверенное содержимое в веб, Markdown или PDF без ещё одного
вызова модели.

## Предложенные доставка, повторы и идемпотентность отчёта

Доставка Kafka — «хотя бы один раз». Контракты не заявляют обработку «ровно один раз».

- Повтор производителем того же логического события использует тот же `event_id`. Новый
  `event_id` означает новое логическое событие.
- LLM-сервис публикует одно завершающее событие `completed` или `failed` на запрос и фиксирует
  смещение входа только после подтверждения публикации Kafka.
- Падение между публикацией и фиксацией может опубликовать тот же завершающий результат повторно.
  Поэтому потребители результатов дедуплицируют по `request_event_id` и принимают только первый
  завершающий результат.
- `retryable` сообщает владельцу процесса, можно ли запланировать новый запрос. Он не заставляет
  LLM-сервис повторять бесконечно. Внутренние попытки исправления схемы/доказательств ограничены
  отдельно.
- Повторный запрос может вызвать повторное вычисление, если у обработчика нет долговременного
  хранилища дедупликации. Для v1 это приемлемо; стабильные ID делают дубликат безопасным для
  последующего состояния.
- Полностью некорректное сообщение без надёжных полей корреляции не может дать корректное событие
  сбоя. Потребитель логирует только нечувствительные метаданные, записывает метрику и фиксирует
  сообщение, чтобы оно не блокировало партицию. При необходимости позже можно добавить топик
  недоставленных сообщений.

## Правила совместимости конверта отчёта

- Добавление необязательного поля обратно совместимо в пределах `event_version: 1`.
- Удаление поля, изменение его смысла/типа, добавление обязательного поля или изменение семантики
  перечисления требует `event_version: 2` и периода миграции.
- Потребители событий отвергают неподдерживаемые версии; они не угадывают и не обрабатывают их
  частично.
- Версии методики оценки, промпта, модели и шаблона отчёта — происхождение результата, а не
  версии схемы Kafka.
- Метки времени, UUID, ID категорий и написание значений перечислений чувствительны к регистру,
  как показано выше.

резервирует место под введение README и переходит максимум по восьми существующим локальным
ссылкам из README на документы (один переход; встроенные и ссылки-сноски). Внешние ссылки никогда

подставляется. Это заменяет прежнюю формулировку, требовавшую оценивать все разделы. Внутри
недоступные оценки остаются null; активный Kafka-адаптер опускает такие разделы в `subgrades`.
Детерминированные проверки обязательных файлов сохраняют прежние правила.
