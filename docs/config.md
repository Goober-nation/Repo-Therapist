# Настройки сервисов: config/app.yaml, переменные окружения и панель администратора

Все настройки, кроме секретов, лежат в [config/app.yaml](../config/app.yaml). Секреты (токены, пароли,
ключи) остаются в `.env` / переменных окружения. Часть настроек администратор может менять на лету во
вкладке «Доступ админа» → «Настройки сервисов».

## Откуда берётся значение: порядок, простыми словами

Для каждой настройки сервис смотрит по порядку и берёт первое найденное:

1. **Переменная окружения** (`.env`, `environment:` в docker-compose, оболочка). Она главнее всего.
2. **Изменение в панели администратора** (хранится в базе, таблица `settings_override`).
3. **Значение в `config/app.yaml`.**
4. **Значение по умолчанию в коде** — если ни один из уровней выше настройку не задаёт.

Окружение побеждает всегда и полностью:

- сервис запоминает окружение один раз при запуске и никогда его не меняет; перечитывание app.yaml и
  изменения из панели меняют только свой уровень;
- переменная, заданная пустой (`FOO=`), тоже считается заданной: app.yaml и панель для неё не
  действуют, работает то, что код делает с пустым значением (обычно — значение по умолчанию);
- `.env` загружается до чтения настроек, поэтому значения из него — тоже окружение;
- настройку, заданную в окружении хотя бы одного сервиса, который её читает, панель показывает как
  «Окружение» и не даёт изменить: Aggregator отклоняет такое изменение, а сам сервис его всё равно бы
  проигнорировал.

Чтобы настройкой управляли app.yaml и панель, её не должно быть в `.env` и в `environment:`.

## Как устроен app.yaml

```yaml
shared:            # читают все сервисы
  clone_timeout: 10m
  static:          # только при запуске
    kafka_brokers: localhost:8053
gateway:           # секция одного сервиса
  rate_limit: 60
  static:
    http_address: ":8080"
admin_editable:    # что можно менять в панели
  - {key: gateway.rate_limit, type: int, min: "1", max: "100000", group: rate_limits, title: "…"}
```

- **Имя ключа = имя переменной окружения** в нижнем регистре: `rate_limit` → `RATE_LIMIT`. Сервисы
  читают те же имена, что и раньше.
- Каждый процесс читает `shared` и свою секцию: `aggregator`, `gateway` (и `frontend`), `rating`,
  `repository`, `grade`, `security_wrapper`, `sourcecraft_wrapper`, `llm` (llm-service и
  llm-summary-service). Одно имя не может встречаться в `shared` и секции сервиса одновременно —
  такой файл не загрузится.
- **`static:`** — настройки, которые читаются только при запуске (адреса, порты, брокеры, топики,
  размеры пулов). Изменение в файле не применится до перезапуска; сервис пишет об этом в лог, а панель
  показывает «Нужен перезапуск».
- Остальные ключи **перечитываются на лету**: сервис проверяет файл каждые 2 секунды (и по `SIGHUP`)
  и применяет новые значения без перезапуска.
- Ключ без значения (`key:`) лишь документирует настройку: действует значение по умолчанию в коде.
- Списки пишутся строкой через запятую, длительности — как в Go: `90s`, `10m`, `2h`.

### Ошибка в файле

Файл проверяется целиком: синтаксис, имена ключей, одно значение на ключ, типы и границы значений из
`admin_editable`. Если файл с ошибкой:

- при запуске сервис не стартует (чтобы не работать на неверно прочитанных настройках);
- при перечитывании сервис пишет ошибку в лог один раз и продолжает работать на последнем исправном
  варианте.

Файл в Docker подключён каталогом (`./config:/app/config:ro`, для LLM — `/app/app-config`), поэтому
правки на хосте видны сервисам сразу, без пересборки образов.

## Панель администратора

Вкладка «Доступ админа» → «Настройки сервисов». Доступны группы:

- **Лимиты запросов** — лимиты Gateway (общий, публичный API, выгрузка), пауза между принудительными
  переоценками, общий лимит новых оценок;
- **Оценка и переоценка** — период и объём плановой переоценки, таймауты клонирования и расчёта,
  блокировка репозитория, ограничения пакетной оценки;
- **LLM** — запрос оценки документации и его таймаут, режим оценки документации, граница приоритета
  рекомендаций (эти настройки влияют на оценку и рекомендации, см.
  [grading/00-overview.md](grading/00-overview.md#эксплуатационные-настройки-влияющие-на-оценку)).

Список ключей, их границы и подписи задаёт секция `admin_editable` в app.yaml; `static:`-ключи туда
попасть не могут.

### Что происходит при сохранении, по шагам

1. Gateway проверяет права администратора и заголовок `X-Admin-Request`, передаёт ключ и значение
   Aggregator по gRPC вместе с хешем администратора.
2. Aggregator проверяет, что ключ есть в `admin_editable`, значение подходит по типу и границам и ни
   один сервис, читающий ключ, не задаёт его в окружении (по отчётам из `config.status` и по своему
   окружению). Если нет — отказ с причиной и запись «Отказ» в журнале.
3. Aggregator записывает значение в `settings_override` и публикует его в Kafka-топик
   `config.updated` (см. [kafka-contracts.md](kafka-contracts.md#настройки-configupdated-и-configstatus)).
4. Каждый сервис, читающий ключ, получает сообщение и применяет значение за секунды, ещё раз проверив
   тип, границы и своё окружение.
5. В журнал действий пишется «Изменение настройки» со старым и новым значением и тем, откуда было
   старое (`override`, `file`, `default`). Значения настроек из панели не секретны.

«Сбросить к app.yaml» удаляет строку из базы и публикует в `config.updated` пустое сообщение
(tombstone): сервисы снова берут значение из файла. В журнале — «Сброс настройки».

### Изменения переживают перезапуски

- Перечитывание app.yaml не трогает изменения из панели: они лежат на уровне выше. Если поменять в
  файле ключ, у которого есть изменение из панели, действует изменение из панели (панель покажет оба).
- При запуске сервис дочитывает `config.updated` до конца (не дольше 15 секунд) и только потом
  начинает работу. Если Kafka недоступна, он стартует на app.yaml и окружении и подхватит изменения,
  когда Kafka ответит.
- Источник истины — таблица в базе: при каждом запуске Aggregator заново публикует все строки и
  отправляет tombstone для ключей, которых в базе нет. Потеря топика ничего не ломает.

## Настройки фронтенда

Фронтенд больше не получает настройки при сборке (`VITE_*` удалены). Gateway отдаёт секцию `frontend`
по публичному `GET /api/config` (Client ID Яндекса, публичный адрес для бейджей, кнопка dev-входа,
время ожидания оценки). Страница читает её один раз при загрузке, так что правка app.yaml действует со
следующей загрузки страницы. Кнопка dev-входа показывается, только если `vite_dev_auth_bypass: true`
**и** на Gateway задан `DEV_AUTH_BYPASS_USER_ID`. Имена переменных прежние, поэтому `VITE_PUBLIC_URL`
в окружении Gateway по-прежнему главнее файла.

## Как проверить на своей машине

```bash
docker compose up -d --build
# Источники значений при запуске: в логе каждого сервиса строка "config: ... sources: ..."
docker compose logs go-services | grep "config:"
# Перечитывание: поменяйте gateway.rate_limit в config/app.yaml и через 2-3 секунды
docker compose logs go-services | grep "reloaded"
# Окружение главнее: RATE_LIMIT=7 в .env -> после перезапуска панель покажет "Окружение"
```

API панели: `GET /api/admin/settings`, `PUT /api/admin/settings/{key}` с телом `{"value": "90"}`,
`DELETE /api/admin/settings/{key}` (см. [api_docs.md](api_docs.md)).
