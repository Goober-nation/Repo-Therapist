# Документация (15%, публичная)

**Статус: реализовано** — контракт `repo.docs.grade.requested` → `repo.docs.graded`
(`docs/kafka-contracts.md`).

**По умолчанию оценка документации идёт без модели.** В `config/app.yaml` стоит
`llm.llm_docs_mode: algorithmic`: оценивается только наличие разделов, качество текста не оценивается
(подробности ниже, «Оценка без модели»). AI-summary и рекомендации делает модель. Чтобы вернуть оценку
моделью, поставьте `auto` в app.yaml или во вкладке «Доступ админа» → «Настройки сервисов»; перезапуск не
нужен, режим применяется к следующему запросу. Переменная `LLM_DOCS_MODE` в окружении главнее и того, и
другого (см. [../config.md](../config.md) и
[00-overview.md](00-overview.md#эксплуатационные-настройки-влияющие-на-оценку)).

## Оценка без модели (режим по умолчанию в Compose), по шагам

1. LLM-сервис читает репозиторий из S3 и сам выбирает тот же набор документов, что и для модели
   (README, документы по ссылкам из README, CONTRIBUTING, CODEOWNERS и т. д.). Модель не вызывается.
2. Обязательные файлы (README, LICENSE и другие) проверяются детерминированно, как обычно: файл
   есть и непустой — баллы начисляются по правилам рубрики, иначе 0.
3. Для каждого раздела рубрики (назначение, локальный запуск, сборка, тесты, пример и др.)
   ищется, есть ли он среди документов: заголовок раздела или признаки его содержимого.
4. Найден раздел — он получает **80% своих баллов** (качество неизвестно, поэтому полный балл не
   ставится). Не найден — 0 баллов и один недостаток для рекомендации. Раздел, который не
   применим к проекту (например, сборка у проекта без сборки), в расчёт не входит.
5. Согласованность документов (команды из инструкции и скрипты проекта, ссылки) требует сравнения
   смысла, поэтому не оценивается: такие проверки не входят ни в набранные, ни в возможные баллы.
6. Оценка категории = 100 × набранные баллы / возможные баллы по проверкам, которые оценивались.
   Разделы рубрики получают такие же проценты.
7. Ответ помечается `method: "algorithmic"`, на карточке «Документация» появляется надпись
   «Упрощённая оценка: проверено только наличие разделов», а в конец рекомендаций добавляется
   пометка об упрощённом методе (приоритет `low`).

Следствие: пока модель выключена, раздел получает не больше 80% своих баллов, поэтому оценка
документации у репозиториев с полным набором разделов заметно ниже 100. Это сознательно: проверка
наличия не должна выдаваться за проверку качества.

## Как вычисляется оценка (по шагам)

1. Grade service публикует `repo.docs.grade.requested` для репозитория и продолжает оценивать
   остальные категории, пока ждёт ответа (не дольше таймаута LLM, по умолчанию 70 с).
2. LLM-сервис читает репозиторий из S3 и просит модель его оценить. В режиме `LLM_DOCS_MODE=auto`
   (сейчас по умолчанию `algorithmic`, см. выше), если на пути модели что-то сломалось — сам вызов (провайдер недоступен,
   лимит запросов, таймаут 60 с, фильтр содержимого, ответ неверного формата) или превращение
   ответа модели в результат, — сервис оценивает тот же репозиторий **алгоритмически**
   (только наличие разделов, без оценки качества) и отправляет эту оценку: каждый найденный раздел
   получает 80% своих баллов (качество неизвестно), отсутствующий — 0, обязательные файлы
   оцениваются как обычно, согласованность не оценивается. Ответ помечается полем
   `method: "algorithmic"` (оценка модели — `method: "llm"`), а в конец рекомендаций добавляется
   пометка, что использован упрощённый метод.
   `LLM_DOCS_MODE=algorithmic` всегда использует этот метод, `LLM_DOCS_MODE=llm` никогда не
   переключается на него и сообщает об ошибке.
3. Если ответ не пришёл вовремя → весь раздел «Документация» получает **нет данных**.
4. Если в ответе непустое поле `error` или `grade` равен `null` → весь раздел «Документация»
   получает **нет данных**; subgrades и advice игнорируются, код ошибки пишется в лог. В режиме
   `auto` это бывает, только если не удалось прочитать сам репозиторий (например,
   `S3_PREFIX_NOT_FOUND`), запрос некорректен или сбоит и алгоритмическая оценка.
5. Иначе `grade` из ответа (0–100) без изменений берётся как оценка категории; `subgrades`
   показываются как метрики только для отображения и не пересчитывают оценку. `method` из ответа
   копируется в объект категории `documentation` в `grading.results` (неизвестное значение
   отбрасывается). Если `method` равен `"algorithmic"`, фронтенд пишет на карточке документации
   «Упрощённая оценка: проверено только наличие разделов». На саму оценку `method` не влияет.
6. Рекомендации по документации берутся из `advice` ответа: код недостатка становится
   `metric_id`, приоритет передаётся как есть (см. «Приоритеты рекомендаций» ниже).
7. Раздел «Документация» без данных исключается из общей оценки, а веса остальных категорий
   перенормируются — так же, как для любой другой категории без данных.

## Приоритеты рекомендаций

Приоритет задаётся для каждого кода недостатка в `backend/llm-service/config/advice.yaml` и
не зависит от оценки:

1. `high` — без этого читатель не поймёт проект или не сможет его запустить: нет README
   (`DOC_README_MISSING`/`_EMPTY`), назначения (`DOC_PURPOSE_*`), инструкции запуска
   (`DOC_LOCAL_RUN_MISSING`, `DOC_LOCAL_RUN_COMMANDS_INCOMPLETE`), LICENSE, или команда в
   инструкции не совпадает со скриптами проекта (`DOC_COMMAND_INCONSISTENT`, `DOC_SCRIPT_NOT_FOUND`).
2. `medium` — нет основного раздела (возможности, сборка, тесты, пример использования), неполные
   требования/зависимости/настройки запуска, битая ссылка, расхождение настроек; запасной текст
   раздела без конкретного кода (`DOC_SECTION_<РАЗДЕЛ>`) — тоже `medium`.
3. `low` — детали уже существующего раздела (проверка запуска, результат сборки, окружение и
   состав тестов, входные данные и результат примера, обзор структуры, навигация, описание
   компонента), CONTRIBUTING, CODEOWNERS и пометка `DOC_ALGORITHMIC_NOTICE`.
4. `critical` для документации не используется: её недостатки не создают немедленного риска.

## Что измеряется

Качество документации и соблюдение лучших практик: наличие README и его *качество* (а не только
наличие), LICENSE, инструкции по локальному запуску, инструкции по сборке/тестированию, структура
проекта, CONTRIBUTING, CODEOWNERS.

## Источник данных

**Основной путь — оценка LLM, запасной — детерминированный.** Grade service передаёт LLM-сервису через Kafka ссылку на содержимое репозитория, уже лежащее в S3, и
получает обратно оценку. LLM-сервис сам выбирает фрагменты документации (README, CONTRIBUTING,
CODEOWNERS, инструкции по сборке/запуску/тестам, структура каталогов). Модель оценивает качество;
запасной путь проверяет только наличие разделов. Обоснование: критерии документации из ТЗ §3.1
включают суждения о качестве («действительно ли README полезен»), которые проверки наличия
делают плохо, и LLM-сервис уже есть в архитектуре именно для таких вызовов.

**Проверено напрямую по PDF ТЗ (§3.1): обход внешних сайтов документации не требуется
и не подразумевается.** Каждый перечисленный критерий — артефакт внутри репозитория, доступный из
дерева, которое repository-service уже загрузил в S3 (`UploadDir`); ничего дополнительно скачивать
не нужно.

## Метрики

Обычная таблица неприменима: итоговая оценка категории — это `grade`, который возвращает
LLM-сервис. Внутри LLM-сервис считает её по взвешенным проверкам рубрики (см.
[`../documentation-grading.md`](../documentation-grading.md)) и отдаёт по Kafka `subgrades` —
целочисленные проценты по разделам рубрики. Grade service показывает их только как метрики и не
пересчитывает по ним оценку.

## Нет данных vs. настоящий ноль

- Порога минимального содержимого нет: принцип 4 в `00-overview.md` не реализован как гейт, поэтому почти
  пустой репозиторий всё равно оценивается (см. известное ограничение там).
- Если путь модели сбоит или истекает таймаут в режиме `auto`, сервис использует алгоритмическую
  оценку: настоящую, упрощённую, с `method: "algorithmic"` и пометкой в рекомендациях. `NoData` возвращается при
  отсутствии ответа или ответе с непустым `error` / `grade: null`; в режиме `auto` это значит, что
  не удалось прочитать репозиторий, запрос некорректен или сбоила и алгоритмическая оценка.
- Если LLM успешно установила, что README вообще *нет*, это настоящая, жёсткая оценка от LLM, а не
  `NoData`. Та же граница «измерено и плохо» vs. «невозможно измерить», что и в остальных
  категориях, только оценивает LLM, а не формула.
