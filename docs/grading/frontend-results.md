# Динамические результаты категорий во фронтенде

Компонент результатов принимает любые названия категорий и любое их количество. Бэкенд
по-прежнему вычисляет оценки по существующим формулам и весам категорий. Это изменение касается
только проверки и отображения полученных оценок; фронтенд не пересчитывает общий health score.

## Поддерживаемый ввод

`category_scores` принимает словарь или документированный массив словарей. Значения могут быть
числами, `null` или объектами с `score` и необязательными `name`, `description` и `trend`.
`criteria` принимается как альтернативный контейнер; если переданы оба, приоритет у
`category_scores`, даже если он пустой или `null`.

```json
{
  "status": "FINISHED",
  "health_score": 82,
  "category_scores": {
    "Мяу": { "score": 72, "description": "Explanation from the backend" },
    "Architecture": 90,
    "Tests": null
  }
}
```

Ключи сохраняются в точности. Белый список категорий не применяется. Объект может задать
отображаемое `name`; иначе показывается английское название известного ID категории (`activity`,
`issues`, `documentation`, `code_health`, `security`, `ci_cd`, см. `src/metrics.ts`) или сам ключ.
Массив `metrics` объекта (`{id, no_data, raw_value}` из grade-service) показывается как факты,
стоящие за оценкой; доли (0–1) показываются в процентах. Остальные поля игнорируются.

## Как категория попадает на экран

1. Бэкенд вычисляет оценку по формуле этой категории.
2. Фронтенд читает каждую запись категории из переданного контейнера.
3. Конечное число от 0 до 100 округляется для отображения. Ноль — допустимое значение.
4. Отсутствующая, null, нечисловая или выходящая за диапазон оценка отображается как `Нет данных`,
   без полосы оценки.
5. Компонент создаёт одну карточку на категорию с её названием и необязательным описанием.
   Экспорт в Markdown и PDF использует те же названия и оценки.

Для отсутствующих категорий не выдумываются нулевые оценки. Завершённый ответ заменяет предыдущий
набор категорий, в том числе очищает его, если категории не переданы. Ответ в состоянии ожидания
без контейнера категорий сохраняет предыдущие результаты; явно пустой контейнер их очищает. В форме
массива при повторе ключа побеждает последняя запись.

Категории без данных перечисляются в блоке «Нет данных» с причиной: в публичном анализе Security и
CI/CD всегда указаны как доступные только владельцу; в приватном анализе приватного репозитория
у Security подсказка «Анализ безопасности для приватных репозиториев доступен только с Security
Add-on»; иначе причина — источник ничего не вернул. `grade.missing_data` из бэкенда — главный
источник для этого списка.

## Публичная оценка для владельца

С токеном SourceCraft репозиторий из «Моих репозиториев» оценивается приватно (6 категорий). Для
публичного репозитория страница показывает переключатель «Публичная оценка»:

1. Пользователь включает переключатель.
2. Запрос оценки `GET /grading/{org}/{repo}`, её опрос и запрос AI-сводки
   `GET /recommendations/{org}/{repo}` отправляются без заголовка `PAT`.
3. Gateway считает публичную оценку (4 категории), как для любого посетителя.
4. Рядом с переключателем указано, какая оценка показана: приватная (6 категорий) или публичная
   (4 категории).

Выключение переключателя возвращает приватную оценку. Для приватных репозиториев переключатель не
показывается.

## Устаревшая оценка и принудительная переоценка

Оценка, посчитанная больше 7 дней назад, помечается как устаревшая. Это только пометка: Score,
место в рейтинге и сама оценка не меняются, автоматической переоценки нет.

Как решается, устарела ли оценка:

1. Берётся время оценки `graded_at` (из `GET /grading` на странице репозитория, из `GET /ranking` в
   рейтинге).
2. Из текущего времени в браузере вычитается `graded_at`.
3. Разница больше 7 суток (`STALE_GRADE_DAYS` в `frontend/src/metrics.ts`) — оценка устарела. Ровно
   7 суток — ещё нет. Нет времени или оно некорректно — метки нет.
4. Где видна метка: бейдж «Устарела» рядом с уровнем на странице репозитория и приписка «более 7 дней
   назад» к строке «Последний анализ»; бейдж «Устарела» в строке рейтинга; приписка «оценка устарела:
   старше 7 дней» к дате последнего анализа в отчётах Markdown и PDF.

Принудительная переоценка — для вошедших через Яндекс пользователей:

1. На странице репозитория рядом с кнопкой анализа есть переключатель «Принудительно» (без входа он
   не показывается). Включённый переключатель меняет кнопку на «Переоценить».
2. Нажатие отправляет `POST /grading/{org}/{repo}/regrade`. Gateway проверяет сессию и
   ограничение: один пользователь — один раз на репозиторий за `FORCE_REGRADE_COOLDOWN_MINUTES` минут
   (по умолчанию 60).
3. Aggregator запускает оценку, не проверяя, была ли новая активность (обычный запуск без
   переключателя пересчитывает только при новой активности). Общий лимит оценок и уже идущая
   оценка учитываются как обычно.
4. Фронтенд опрашивает `GET /grading`, пока не придёт оценка с новым `graded_at`, и пишет
   «Анализ завершён, оценка обновлена». Если новая оценка не пришла за время опроса — «Переоценка не
   завершилась за отведённое время». Отказы (нет входа, ограничение с числом минут, общий лимит)
   показываются текстом над карточкой.

## Модель AI-сводки

Если `GET /recommendations/{org}/{repo}` вернул поле `model_used`, под AI-сводкой выводится
«Сформировано моделью <название>».

В публичном рейтинге нет оценок по категориям (Gateway возвращает только `public_score`). Он
постраничный на сервере (`GET /ranking`, 100 на страницу): сортировка и фильтр по языку работают
на сервере (фильтры собраны в панель «Фильтры» со счётчиком включённых), а текстовый поиск и фильтр минимальной оценки сужают только загруженную страницу и
сообщают об этом. Отсутствующая общая оценка не проходит фильтр с положительным минимумом.

## Выгрузка отчёта (Markdown и PDF)

Кнопка «Скачать отчёт» на странице репозитория отдаёт один и тот же набор данных в двух видах.
Отчёт строится из того, что уже загружено на странице, и ничего не запрашивает заново.

Что входит, по порядку:

1. Заголовок: репозиторий (со ссылкой), режим анализа (публичный или приватный, все 6 категорий),
   язык, время последнего анализа, давность активности. Поля, которых нет, не выводятся: язык
   «Не указан» и неизвестная активность пропускаются.
2. Repo Health Score и уровень («Здоровый», «Под риском» и т. д.), цвет полосы соответствует уровню.
   Если оценки нет, пишется только «Нет данных», уровень не дублируется. Для публичной оценки — место
   в рейтинге («3 из 27»), если оно загружено.
3. Плашка «Мало данных» с причинами, если оценка помечена как низкодостоверная.
4. Summary AI (с названием модели) или пометка, что сводки нет.
5. Сильные стороны и требует внимания.
6. Категории: оценка, вес в итоговом Score, описание, факты. Документация, оценённая без модели,
   помечена «Упрощённая оценка: проверено только наличие разделов». У категории без оценки факты не
   перечисляются: она описана в блоке «Нет данных» с причиной.
7. Рекомендации, отсортированные по приоритету; у срочных (критический и высокий приоритет) в PDF красная
   полоса слева.
8. История оценки (до 8 последних точек: график и изменение за период) — только для публичной оценки,
   когда история загружена.
9. Углублённая аналитика (фактор автобуса, ревью, ответы на задачи, CODEOWNERS, карта владельцев) — когда
   аналитика загружена; блок без данных объясняет причину тем же текстом, что и страница.

Markdown: таблицы показателей и категорий, спецсимволы в названиях, описаниях и ответах модели
экранируются, чтобы текст репозитория не ломал разметку; путь в рекомендации оформляется кодом.

PDF: A4, шрифт Roboto. Карточки идут по две в ряд одной высоты и переносятся на следующую страницу
целиком; заголовок раздела не остаётся один внизу страницы. Roboto не умеет рисовать эмодзи и некоторые
пробелы и дефисы, которые любит модель (узкий неразрывный пробел, неразрывный дефис): первые
удаляются, вторые заменяются обычными. Слишком длинное имя укорачивается в нижнем колонтитуле.

Приватный отчёт (токен владельца) содержит все 6 категорий и приватные рекомендации. Файл создаётся
в браузере и никуда не отправляется.

## Проверка

Из каталога `frontend` выполните `corepack pnpm run check` (проверка типов, тесты, сборка). Тесты
покрывают сопоставление, отрисовку всей страницы, экспорт в Markdown и PDF, добавление/удаление
категорий, некорректные значения, факты метрик, отсутствующие данные, переходы из ожидания в
завершение и опрос.
