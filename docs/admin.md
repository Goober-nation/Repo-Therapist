# Доступ админа: права администратора и журнал действий

Статус: 2026-10-09, этапы доступа, журнала, пакетной оценки, графиков, расхода LLM и журнала действий
пользователей. Статистика сессий добавляется следующим этапом в ту же вкладку. Расчёт оценок и порядок рейтинга не
затрагиваются.

## Что есть

- **Одна вкладка «Доступ админа»** (`/admin-access`, старая ссылка `/admin` открывает её же). Она в боковом меню
  у всех. Без прав в ней форма пароля; когда права есть, в ней же появляются инструменты администратора. Отдельной
  вкладки администратора нет.
- **Журнал действий** — запись событий администраторов и отказов в доступе, с фильтром по результату; по 10 записей на
  странице, кнопки «Назад» и «Дальше» (общее число страниц не показывается: журнал листается по курсору, как в
  `GET /admin/audit`); виден в этой вкладке только администратору. Смена фильтра или новая запись возвращают на первую
  страницу.
- **Действия пользователей** — отдельный блок под журналом: кто и когда запросил оценку репозитория или
  рекомендации модели (хеш аккаунта, без имени), с фильтрами по действию и результату и тем же листанием по 10
  записей. Подробнее — в разделе «Журнал действий пользователей».
- **Пакетная оценка** — администратор выбирает публичные репозитории из полного списка (по языку, оценке, давности
  последней оценки или своим списком), задаёт, сколько из них взять, и при желании ограничивается уже оценёнными;
  смотрит, сколько их и сколько это займёт, запускает пакет и следит за ним: пауза, продолжение, отмена, список
  репозиториев с ошибками. Подробнее — в разделе ниже.
- **Графики работы сервиса** — десять графиков из Prometheus: нагрузка, время ответа, запуски и результаты оценок,
  отказы по лимиту, запросы к LLM, пакеты, отказы администратору. Ниже блок «Расход LLM»: токены за сутки и за час,
  на что они уходят, вызовы модели и их время (токены, без денег). Подробнее — [metrics.md](metrics.md).
- **Права администратора** даются двумя способами: списком Яндекс-идентификаторов в настройках или
  паролем (см. ниже). Схема пользователей не менялась.

## Кто администратор и как это проверяется, простыми словами

1. Достаточно одной из двух настроек Gateway: списка `ADMIN_YANDEX_IDS` (через запятую) или пароля
   `ADMIN_PASSWORD`. Ключ хеша участников в журнале берётся из `AUDIT_HASH_SECRET`, а если его нет, выводится из
   этих настроек (журнал не должен хранить сырой идентификатор). Тогда хеши меняются вместе с настройками;
   чтобы они не менялись, задайте `AUDIT_HASH_SECRET`. В логе при запуске Gateway пишет, включены ли
   админские маршруты.
2. Пользователь входит через Яндекс как обычно, Gateway создаёт сессию и ставит куку `session_id`
   (`HttpOnly`, `Secure`, `SameSite=Lax`).
3. На админском маршруте Gateway читает куку, находит пользователя по сессии и сверяет его
   Яндекс-идентификатор со списком. Нет сессии или она неизвестна — `401`; пользователь не из списка —
   `403`. Сбой Redis или базы — `5xx`, а не «не администратор».
4. `GET /admin/me` отвечает `{is_admin}` **всегда `200`**, в том числе посетителю без сессии: по нему
   интерфейс решает, показывать ли вкладку, и ничего не пишет в журнал.
5. Запросы, меняющие состояние (пакетная оценка, обновление списка репозиториев), дополнительно требуют заголовок
   `X-Admin-Request: 1`. Страница на другом сайте не может добавить свой заголовок к запросу без
   предварительной CORS-проверки, а админские маршруты её не разрешают, поэтому одной куки недостаточно,
   чтобы подделать действие администратора. Ответы админских маршрутов не кэшируются
   (`Cache-Control: no-store`) и не отдают `Access-Control-Allow-Origin`.

## Доступ по паролю: простыми словами

1. Пароль задаётся в настройках Gateway переменной `ADMIN_PASSWORD` (открытым текстом, см. «Ограничения»).
   Больше ничего задавать не нужно. Без пароля вкладка «Доступ админа» объясняет, что вход по паролю не настроен.
2. **Нужен вход через Яндекс.** Права привязываются к вашей учётной записи; без входа вкладка просит
   войти, а запрос пароля даёт `401`. Гостевые учётные записи не создаются.
3. `POST /admin/unlock` с телом `{"password": "..."}` и заголовком `X-Admin-Request: 1`. Пароль берётся
   только из тела запроса, не из адреса, и нигде не логируется и не возвращается в ответе. Сравнение
   выполняется за постоянное время: оба значения сначала хешируются SHA-256.
4. Верный пароль даёт права **этой сессии**: Gateway сохраняет в Redis отметку `admin_grant:<сессия>` на
   то же время, что живёт сессия (`SESSION_TTL`, по умолчанию 24 часа). Кончилась сессия — кончились и
   права. В отметке лежит не пароль, а отпечаток: HMAC от пароля с ключом хеша (`AUDIT_HASH_SECRET` или выведенным ключом).
   **Смена `ADMIN_PASSWORD` сразу отзывает все выданные права**: отпечаток старой отметки перестаёт
   совпадать.
5. **Блокировка.** Неверные пароли считаются отдельно по IP и по учётной записи. После
   `ADMIN_UNLOCK_MAX_ATTEMPTS` (5) неверных подряд ключ блокируется на `ADMIN_UNLOCK_LOCK` (15 минут):
   любой запрос получает `429` с `Retry-After`, и пароль **не проверяется**, даже верный — по ответу нельзя
   понять, угадан ли он. Заблокированный IP блокирует любую учётную запись с него, а заблокированная
   учётная запись — любой IP. Верный пароль сбрасывает счётчики. Счётчик неверных попыток обнуляется, если
   за период блокировки новых не было.
6. `POST /admin/lock` снимает права, полученные по паролю. Администратор из списка остаётся
   администратором.
7. Каждая попытка пишется в журнал (см. ниже), пароль — никогда.

## Выход из аккаунта и потерянная сессия

- **Кнопка «Выйти»** в верхней панели рядом с именем. `POST /auth/logout` (с заголовком `X-Admin-Request: 1`)
  удаляет сессию в Redis, снимает право, выданное по паролю, и стирает куку `session_id`. Повторный выход, выход без
  сессии и выход с уже удалённой сессией тоже успешны. Если право по паролю было, в журнал пишется `admin.lock` с
  пометкой «при выходе из аккаунта». Интерфейс забывает всё, что связано с пользователем: сохранённый профиль,
  токен SourceCraft и загруженные с ним приватные данные, и открывает рейтинг. Локальный выход не ждёт ответа
  сервера: даже если запрос не дошёл, пользователь выглядит вышедшим, а сессия на сервере доживёт свой срок.
- **Потерянная сессия.** Имя в верхней панели берётся из профиля, который хранится только во вкладке
  браузера, а сам вход — это сессия на сервере (кука `session_id`, ключ в Redis). Сессия может пропасть раньше
  профиля: истёк срок, перезапущен Redis без сохранения, куку не приняли. Раньше интерфейс при этом продолжал
  показывать вход, а Gateway не узнавал пользователя. Теперь `GET /admin/me` всегда сообщает `signed_in` по
  реальной сессии (и при выключенных админских настройках), а интерфейс при `signed_in: false` сам убирает
  сохранённый профиль и показывает кнопку входа. Неизвестный ответ (запрос не прошёл или ещё идёт) вход не
  отменяет, а ответ, полученный до входа, после входа не используется.

## Пакетная оценка

Нужна, когда оценки хочется получить или обновить не по расписанию: после правки правил, для одного языка, для
давно не оценивавшихся репозиториев, для ещё не оценённых или для списка, который администратор перечислил сам.
До 2026-10-09 называлась «пакетная переоценка» и выбирала только из уже известных сервису репозиториев.

**Как это работает, шаг за шагом:**

1. В блоке «Пакетная оценка» вкладки «Доступ админа» укажите **«Не больше репозиториев»** — это поле обязательно.
   Верхней границы нет, если на стенде не задан `BATCH_GRADING_MAX_LIMIT`: тогда больше этого числа указать нельзя,
   подпись поля показывает предел, а запрос сверх него отклоняется (`400` с `code` `limit_too_high`).
2. При желании задайте условия. Все они необязательны и складываются: репозиторий должен подойти под все заданные.
   - языки (без учёта регистра);
   - оценку «от» и «до» по сохранённой публичной оценке (репозиторий без оценки под эти условия не подходит);
   - «последней оценке больше N дней» (репозитории, которые не оценивались вообще, тоже подходят);
   - свой список (до 200): `организация/репозиторий` или ссылка на репозиторий в SourceCraft
     (`https://sourcecraft.dev/организация/репозиторий`, можно без `https://` и `www`, с `.git` или путём после
     названия). Ссылки превращаются в `организация/репозиторий` прямо в форме, повторы убираются после этого; ссылка
     на другой сайт или без названия репозитория не принимается.

   Без условий подходят все публичные репозитории.
3. Отметка **«Только переоценка»** оставляет только репозитории, у которых уже есть публичная оценка. Без неё в пакет
   попадают и ещё не оценённые: они оцениваются впервые.
4. Репозитории выбираются из сохранённого списка публичных репозиториев (см. «Список публичных репозиториев» ниже).
   Пока список пуст, выбор идёт из репозиториев, которые сервис уже видел. Из подошедших берутся первые по рейтингу
   SourceCraft, не больше указанного числа (рейтинг складывается из реакций пользователей, отдельного поля «лайков» в
   API нет).
5. «Проверить» — пробный расчёт: сколько репозиториев подошло под условия и сколько из них возьмёт ограничение,
   первые из них, ориентировочное время и сколько, скорее всего, будет пропущено без новой активности (см. шаг 6).
   Репозитории из своего списка, которых нет среди подошедших, называются, только если ограничение никого не
   отрезало. Ничего не запускается и не записывается. Любое изменение условий сбрасывает пробный расчёт:
   «Запустить» доступно только после проверки именно этих условий.
6. «Запустить» создаёт пакет. Репозитории оцениваются по очереди, **не больше трёх одновременно**
   (`BATCH_GRADING_CONCURRENCY`); каждый проходит тот же путь, что и обычная оценка (блокировка репозитория,
   запрос в grade-service через Kafka), поэтому результат попадает в рейтинг, как всегда. Репозитории, которых
   сервис ещё не видел, сначала сохраняются. Пакет считается по числу «обработано из всего».

   **Проверка новой активности.** Прямо перед оценкой каждого репозитория Aggregator запрашивает в SourceCraft его
   текущее `last_updated` и сравнивает со временем последней публичной оценки. Если активности после оценки не было,
   репозиторий **пропускается** (код `no_activity`, «нет новой активности с последней оценки») и не оценивается.
   Простыми словами:
   1. Репозиторий ни разу не оценивался — оценивается.
   2. Иначе берётся `last_updated` из SourceCraft. Его сдвигают коммиты в любую ветку, изменения задач и некоторые
      другие события (реакции, настройки). Поэтому проверка не пропускает новые коммиты и задачи, но иногда
      оценивает репозиторий заново без изменений в коде — это безопасная сторона ошибки.
   3. `last_updated` позже последней оценки — оценивается; не позже — пропускается.
   4. SourceCraft не ответил или время неизвестно — репозиторий оценивается (пропуск требует точного ответа).

   Отметка **«Принудительная оценка»** (`force`) отключает эту проверку: оцениваются все выбранные репозитории.
7. **Пауза**: репозитории, которые уже оцениваются, дооцениваются, новые не берутся; «Продолжить» возобновляет.
   **Отмена** (с подтверждением): остальные репозитории пропускаются, уже идущие дооцениваются.
8. Репозиторий, который не удалось оценить, остаётся в списке «С ошибкой» с кратким кодом причины:
   не удалось запустить оценку, оценка завершилась ошибкой, результат не пришёл за `BATCH_GRADING_ITEM_TIMEOUT`
   (15 минут по умолчанию), новая оценка не появилась. Остальные репозитории пакета это не останавливает.

**Ограничения и защита:**

- Одновременно выполняется **один** пакет (запущенный или на паузе). Пока он не завершится или не будет отменён и
  пока идущие репозитории не дооценятся, новый не запускается (`409`).
- В пакет попадают только **публичные** репозитории; приватные не выбираются никогда. Если репозиторий перестал быть
  публичным, пока пакет шёл, он пропускается. Токены пользователей пакет не использует.
- Размер пакета ограничен полем «Не больше репозиториев» и, если задан, пределом стенда `BATCH_GRADING_MAX_LIMIT`
  (по умолчанию `0` — без предела; удобно для демо и общего стенда). Весь список (около 28 500
  репозиториев) при трёх оценках одновременно — это порядка десяти дней работы: смотрите на оценку времени в
  пробном расчёте.
- Пакет хранится в базе (таблицы `grading_batches` и `grading_batch_items`; созданы миграцией 000009, переименованы
  миграцией 000011), поэтому перезапуск Aggregator его не теряет: идущий пакет продолжается, пакет на паузе
  остаётся на паузе, репозитории, которые оценивались в момент остановки, ставятся в очередь заново.
- Пакет записывает хеш запустившего администратора, а не его идентификатор.
- Пока идёт пакет, блок обновляется сам (раз в 3 секунды); история — последние 10 пакетов. У пакетов, запущенных до
  переименования, ограничение и «только переоценка» в истории не показываются.

**В журнал попадают** `batch_grading.start`, `.pause`, `.resume`, `.cancel` (участник — `admin`) и
`batch_grading.complete` (участник — `system`); объект — номер пакета, в подробностях число репозиториев и условия
(из своего списка — только число). Записи до переименования остались с действиями `regrade.batch.*` и показываются с
прежними подписями. Записи пишет Aggregator сразу после действия; сбой записи в журнал не отменяет само действие, он
остаётся в логе сервиса.

## Список публичных репозиториев

SourceCraft отдаёт список всех публичных репозиториев только постранично (`GET /repos`, до 100 на страницу; на
2026-10-09 это около 28 500 репозиториев, примерно 285 страниц). Раньше плановая переоценка запрашивала его целиком
при каждом запуске и упиралась в ограничение: без `page_size` SourceCraft отдаёт по 20 на страницу, а число страниц
ограничено `SOURCECRAFT_MAX_PAGES` (50), поэтому видно было не больше 1000 репозиториев. Теперь список хранится в
базе и обновляется по запросу администратора.

**Как это работает, шаг за шагом:**

1. В блоке «Список репозиториев» вкладки «Доступ админа» видно, сколько репозиториев в сохранённом списке, когда он
   обновлён и кем (администратором или автоматически при запуске).
2. «Обновить список» запускает обновление. Aggregator по одной запрашивает страницы у sourcecraft-wrapper
   (`ListPublicReposPage`, 100 репозиториев на страницу, в обычном порядке платформы, а не по рейтингу: так список не
   сдвигается, пока его листают) и складывает их во временную таблицу. В блоке видно, сколько страниц и
   репозиториев уже загружено; он обновляется сам раз в 3 секунды. Обычно это занимает две-три минуты.
3. Когда SourceCraft вернул последнюю страницу, временная таблица одной транзакцией заменяет сохранённый список.
   Повторы убираются: каждый репозиторий попадает в список один раз. В список попадают только публичные.
4. Если что-то пошло не так, сохранённый список **не меняется**, а обновление получает код причины:
   - `wrapper_error` — SourceCraft или wrapper не ответили на страницу;
   - `too_many_pages` — страниц больше `CATALOG_MAX_PAGES` (2000 по умолчанию, то есть 200 000 репозиториев);
   - `page_loop` — SourceCraft вернул уже пройденную страницу;
   - `empty_listing` — в ответе не нашлось ни одного публичного репозитория (пустой список не заменяет старый);
   - `store_error` — сбой базы данных;
   - `interrupted` — Aggregator перезапустился во время обновления.
5. «Остановить» (с подтверждением) прерывает идущее обновление; сохранённый список остаётся прежним.

**Кто пользуется списком:**

- **Плановая переоценка** берёт из списка первые `GRADING_REGRADE_LIMIT` репозиториев по рейтингу SourceCraft
  (500 по умолчанию, `0` — все) вместо запроса к SourceCraft при каждом запуске. Пошагово:
  1. Берутся первые `GRADING_REGRADE_LIMIT` репозиториев списка по рейтингу.
  2. Репозиторий без публичной оценки отправляется на оценку.
  3. У оценённого Aggregator спрашивает в SourceCraft его текущее `last_updated` — та же проверка, что у пакетной
     оценки: дата активности в списке устаревает вместе со списком.
  4. Была активность после оценки (или у оценки нет более новых данных аналитики) — репозиторий оценивается заново;
     не было — пропускается. SourceCraft не ответил — оценивается.
- **Пакетная оценка** выбирает репозитории из списка по всем своим условиям.
- Пока список пуст (сразу после установки), плановая переоценка запрашивает список у SourceCraft напрямую, а
  пакетная оценка выбирает из репозиториев, которые сервис уже видел.

**Ограничения и защита:**

- Одновременно идёт **одно** обновление; повторный запрос — `409` с `code` `refresh_active`.
- Если при запуске Aggregator список пуст, первое обновление начинается само (в журнале и в блоке — «автоматически
  при запуске»). Обновление, прерванное перезапуском, при следующем запуске помечается как `interrupted`.
- Список устаревает: новые репозитории SourceCraft в нём появятся только после следующего обновления. Оценка
  репозитория по ссылке от пользователя от списка не зависит.
- Запросы идут с токеном сервиса (`SERVICE_TOKEN`); без него обновление не запускается.
- Таблицы: `public_repo_catalog`, `public_repo_catalog_staging`, `catalog_refreshes` (миграция 000010). Обновление
  записывает хеш запустившего администратора, а не его идентификатор.

**В журнал попадают** `catalog.refresh.start` и `.cancel` (участник — `admin`), `catalog.refresh.complete` и
`catalog.refresh.fail` (участник — `system`, у неудачного — исход `error` и код причины); объект — номер обновления.

## Журнал действий

Запись: время, вид участника (`admin` / `user` / `anonymous` / `system`), его хеш, действие
(`admin.denied`, дальше `batch_grading.start`, `catalog.refresh.start` и т. п.), объект (вид и значение), результат
(`ok` / `denied` / `error`) и короткие подробности (например, причина отказа).

**Что записывается сейчас:**

- отказ в доступе к админскому маршруту (`admin.denied`) с причиной `no_session`, `invalid_session` или
  `not_admin`; запись содержит путь маршрута без строки запроса;
- вход по паролю (`admin.unlock`): успех (`ok`, `via: password`, участник — `admin`) и отказ (`denied`,
  причина `wrong_password`, `locked`, `no_session` или `invalid_session`);
- снятие прав (`admin.lock`), только если права были;
- запуск, пауза, продолжение, отмена и завершение пакетной оценки (`batch_grading.*`, до 2026-10-09 —
  `regrade.batch.*`, см. выше);
- запуск, остановка, завершение и сбой обновления списка репозиториев (`catalog.refresh.*`, см. выше).

**Что не записывается никогда:**

- токены и PAT, куки и идентификаторы сессий;
- сырой Яндекс-идентификатор: вместо него первые 16 символов HMAC-SHA256 от него с ключом
  `AUDIT_HASH_SECRET`;
- IP-адрес и строка запроса;
- название закрытого репозитория: для него в журнале будет хеш или метка «закрытый репозиторий».

**Защита от засорения.** Отказы от одного IP пишутся не чаще `ADMIN_DENIED_LOG_LIMIT` раз за
`ADMIN_DENIED_LOG_WINDOW` (по умолчанию 5 за 10 минут); это относится к отказам в доступе, к попыткам без
сессии и к отказам из-за блокировки. Неверные пароли в этот лимит не входят: их и так ограничивает
блокировка. Ответ клиенту от лимита записи не меняется. Сбой записи
журнала тоже не меняет ответ.

**Хранение.** Только Aggregator пишет в таблицу `audit_log` (Gateway передаёт события ему по gRPC) и раз в
час удаляет записи старше `AUDIT_RETENTION_DAYS` (по умолчанию 30; `0` — хранить всегда). Aggregator
проверяет каждое событие: действие — слова через точку строчными буквами, не длиннее 64 символов; хеш —
шестнадцатеричная строка; подробности — небольшой JSON-объект до 2 КБ.

## Журнал действий пользователей

Те же записи в `audit_log`, что и у администраторов, но в отдельном блоке: журнал администраторов показывает всё,
кроме действий пользователей, блок пользователей — только их (`GET /admin/audit?scope=admin` и `scope=users`;
без `scope` — всё, как раньше).

**Что записывается** — два действия, которые что-то запускают или тратят:

| Действие | Когда | Подробности |
|---|---|---|
| `grading.request` | запрос `GET /grading/{org}/{repo}` | `state`: `ready` (оценка есть) или `pending` (считается); при отказе или ошибке — `reason`: `grading_limit` (общий лимит оценок), `no_access`, `not_found`, `interrupted`, `failed` |
| `recommendations.request` | запрос `GET /recommendations/{org}/{repo}` | то же |

Результат записи: `ok` (ответ или «считается»), `denied` (нет доступа, общий лимит оценок), `error` (не найден,
прервана, сбой). Обычные просмотры (рейтинг, значки, история, выгрузки, статистика) не записываются, как и входы и
выходы из аккаунта.

**Кто.** Вошедший в аккаунт — вид `user` и тот же хеш Яндекс-идентификатора, что у администраторов (одного человека можно
связать между записями, имя не видно). Без входа — `anonymous` без хеша.

**Что за объект.** Запрос с токеном SourceCraft может относиться к закрытому репозиторию, поэтому для него и для любого
отказа в доступе в журнале лежит не `org/repo`, а хеш (`access: token`; для отказа — `access: public`, а объект всё равно
хеш). Только запрос без токена, получивший ответ про открытый репозиторий, пишется как `org/repo`. Хеш один и тот же для
одного репозитория, так что повторы видны. Названия, не похожие на обычные (пробелы, длиннее 64 символов, не латиница), не
записываются совсем; не записываются и запросы, остановленные лимитом запросов с IP (их считают метрики), и запросы с
неверными параметрами.

**Защита от засорения.** Одинаковое действие одного участника над одним объектом с одним результатом пишется не чаще
раза за `USER_AUDIT_WINDOW` (по умолчанию 5 минут): страница, которая опрашивает оценку, оставляет одну запись, а смена
состояния (`pending` → `ready`) — новую. Для анонимов участником считается IP, но в журнал он не попадает. `USER_AUDIT_WINDOW=0`
выключает запись действий пользователей. Сбой записи ответ не меняет. Хранение — как у остального журнала: 30 дней.

## Маршруты

| Маршрут | Доступ | Ответ |
|---|---|---|
| `GET /admin/me` | любой | `{is_admin, signed_in, unlock_available, via_password}`, всегда `200`; `signed_in` — действительна ли сессия, независимо от админских настроек; по нему интерфейс решает, что показывать, и замечает потерянную сессию |
| `POST /auth/logout` | любой | заголовок `X-Admin-Request: 1`; завершает сессию, снимает право по паролю, стирает куку; `200 {"signed_out": true}` и при отсутствии сессии; `403` без заголовка, `429` при превышении лимита запросов |
| `POST /admin/unlock` | любой, нужна сессия | тело `{"password"}` и заголовок `X-Admin-Request: 1`; `200` и тот же ответ, что у `/admin/me`; `401` без сессии, `403` неверный пароль, `400` пустой или слишком длинный (больше 256 байт) пароль или битое тело, `429` с `Retry-After` при блокировке |
| `POST /admin/lock` | любой, нужна сессия | заголовок `X-Admin-Request: 1`; снимает права, полученные по паролю; `200` и ответ как у `/admin/me`; повторный вызов ничего не меняет |
| `GET /admin/audit?limit=&before_id=&action=&outcome=&scope=` | админ | `{entries: [{id, at, actor_kind, actor, action, target_kind, target, outcome, details}], next_before_id}`; новые записи первыми; `limit` по умолчанию 50, не больше 200; `before_id` — курсор из `next_before_id` предыдущей страницы (`0` — страниц больше нет); `action` — точное действие или префикс с точкой на конце (`admin.`); `outcome` — `ok` / `denied` / `error`; `scope` — `admin` (всё, кроме действий пользователей) или `users` (только `grading.` и `recommendations.`), без него — всё; неверное значение — `400` |
| `GET /admin/metrics/{name}?range=1h\|6h\|24h\|7d` | админ | график работы сервиса `{name, unit, step_seconds, generated_at, series}`; период по умолчанию сутки; `400` на неверный период, `404` на неизвестный график, `503` с `code` `metrics_off` или `metrics_unavailable`; без кэша; подробности — [metrics.md](metrics.md) |
| `POST /admin/grading/preview` | админ | тело — условия `{limit, languages, min_score, max_score, older_than_days, repos, only_regrade, force}` (`limit` обязателен, не меньше 1) и заголовок `X-Admin-Request: 1`; `{matched, count, sample, unmatched, estimate_seconds, inactive}` (`matched` — сколько подошло под условия, `count` — сколько из них возьмёт ограничение) (`inactive` — оценка числа пропусков без новой активности, 0 при `force`); ничего не запускает; `400` с `code` `invalid_filter` на неверные условия |
| `POST /admin/grading/batches` | админ | те же условия и заголовок; запускает пакет, `201` и пакет `{id, created_at, finished_at, status, actor, filter, total, pending, running, ok, failed, skipped}`; `400` с `code` `invalid_filter`, `nothing_selected` или `limit_too_high`, `409` с `code` `batch_active`, пока другой пакет не закончился |
| `GET /admin/grading/batches?limit=` | админ | `{batches: [...], max_limit}`, новые первыми, по умолчанию 10, не больше 50; `max_limit` — предел стенда `BATCH_GRADING_MAX_LIMIT`, `0` — без предела |
| `GET /admin/grading/batches/{id}` | админ | `{batch, failures: [{repo, error}]}` (не больше 100 ошибок); `404` с `code` `batch_not_found`; вместо номера можно указать `current`: идущий пакет или последний, а если пакетов ещё не было — `200` с `batch: null` |
| `POST /admin/grading/batches/{id}/{pause\|resume\|cancel}` | админ | заголовок `X-Admin-Request: 1`; ответ — пакет; `409` с `code` `bad_state`, если действие не подходит состоянию (пауза уже остановленного), `404`, `400` на неизвестное действие |
| `GET /admin/catalog` | админ | `{size, updated_at, current, last_completed}`: размер и время сохранённого списка, идущее (или последнее) обновление и обновление, из которого получен список; обновление — `{id, started_at, finished_at, status, trigger, actor, pages, repos, error}`, `status` — `running` / `completed` / `failed` / `cancelled`, `trigger` — `admin` / `startup`; до первого обновления `size` 0, остальное `null` |
| `POST /admin/catalog/refresh` | админ | заголовок `X-Admin-Request: 1`; запускает обновление, `202` и обновление; `409` с `code` `refresh_active`, пока идёт другое |
| `POST /admin/catalog/refresh/cancel` | админ | заголовок `X-Admin-Request: 1`; останавливает идущее обновление, ответ — обновление; `409` с `code` `refresh_not_running`, если ничего не идёт |

## Настройки

| Переменная | Где | По умолчанию | Назначение |
|---|---|---|---|
| `ADMIN_YANDEX_IDS` | Gateway | пусто | Яндекс-идентификаторы администраторов через запятую |
| `ADMIN_PASSWORD` | Gateway | пусто | пароль для вкладки «Доступ админа», открытым текстом; пусто — вход по паролю выключен |
| `ADMIN_UNLOCK_MAX_ATTEMPTS`, `ADMIN_UNLOCK_LOCK` | Gateway | 5 и 15m | сколько неверных паролей подряд блокируют и на сколько |
| `AUDIT_HASH_SECRET` | Gateway | выводится | необязательный ключ хеша участника в журнале и отпечатка пароля; без него выводится из `ADMIN_PASSWORD` и `ADMIN_YANDEX_IDS` |
| `ADMIN_DENIED_LOG_LIMIT`, `ADMIN_DENIED_LOG_WINDOW` | Gateway | 5 и 10m | сколько отказов с одного IP попадает в журнал |
| `USER_AUDIT_WINDOW` | Gateway | 5m | раз в какой срок пишется одинаковое действие пользователя; `0` — не писать |
| `AUDIT_RETENTION_DAYS` | Aggregator | 30 | срок хранения записей, `0` — без ограничения |
| `PROMETHEUS_URL`, `SERIES_CACHE_SECONDS` | Gateway | `http://prometheus:9090` в compose и 60 | откуда брать числа для графиков и на сколько кэшировать ответ; пусто — графики выключены |
| `BATCH_GRADING_CONCURRENCY` | Aggregator | 3 | сколько репозиториев пакета оцениваются одновременно |
| `BATCH_GRADING_ITEM_TIMEOUT` | Aggregator | 15m | сколько ждать результат одного репозитория |
| `BATCH_GRADING_MAX_LIMIT` | Aggregator | 0 | наибольшее «не больше N репозиториев» в одном пакете; `0` — без предела |
| `CATALOG_MAX_PAGES` | Aggregator | 2000 | наибольшее число страниц (по 100 репозиториев) в одном обновлении списка публичных репозиториев |
| `DEV_AUTH_BYPASS_USER_ID` | Gateway | пусто | только для тестовых стендов: любой токен входит как этот Яндекс-идентификатор, Яндекс не вызывается, cookie сессии без `Secure`; пусто — выключено |
| `VITE_DEV_AUTH_BYPASS` | Frontend (сборка) | пусто | `true` — вместо кнопки Яндекса кнопка «Войти (dev)»; нужна вместе с `DEV_AUTH_BYPASS_USER_ID` |

Обход входа через Яндекс никогда не включается на публичном стенде: любой, кто откроет страницу, войдёт как этот пользователь (и как администратор, если его идентификатор есть в `ADMIN_YANDEX_IDS`).

## Как проверить на своей машине

Вход через Яндекс на локальном стенде может быть не настроен, поэтому сессию можно создать вручную.
Пользователь — запись в таблице `users`, сессия — ключ `session:<id>` в Redis со значением, равным
`users.id`:

```bash
# 1. Запустите Gateway с ADMIN_YANDEX_IDS=my-yid (или с ADMIN_PASSWORD для проверки пароля)
# 2. Создайте пользователя и сессии
docker compose exec -T postgres psql -U $POSTGRES_USER -d $POSTGRES_DB \
  -c "insert into users(id, yandex_id) values ('11111111-1111-1111-1111-111111111111', 'my-yid')"
docker compose exec -T redis redis-cli set session:demo-admin 11111111-1111-1111-1111-111111111111 EX 1800

# 3. Проверка
curl -s -b "session_id=demo-admin" localhost:8080/admin/me          # {"is_admin":true,...}
curl -s -o /dev/null -w "%{http_code}\n" localhost:8080/admin/audit  # 401 без куки
curl -s -b "session_id=demo-admin" localhost:8080/admin/audit        # журнал, отказ из строки выше уже записан
```

В браузере тот же результат даёт кука `session_id=demo-admin`, поставленная вручную. Для проверки пароля
запустите Gateway с `ADMIN_PASSWORD`, создайте так же обычного пользователя (его `yandex_id` не должен быть в
`ADMIN_YANDEX_IDS`) и отправьте пароль:

```bash
curl -s -X POST -b "session_id=demo-member" -H "X-Admin-Request: 1" -H "Content-Type: application/json" \
  -d '{"password":"..."}' localhost:8080/admin/unlock      # 200 и is_admin:true; неверный — 403, после 5 — 429
curl -s -X POST -b "session_id=demo-member" -H "X-Admin-Request: 1" localhost:8080/admin/lock
```

После проверки удалите созданные строки из `users` и ключи `session:*`, `admin_grant:*`,
`admin_unlock:*` из Redis.

## Ограничения

- **Пароль лежит в настройках открытым текстом** (`ADMIN_PASSWORD` в `.env` и в окружении контейнера).
  Любой, кто его знает и вошёл через Яндекс, получает права до конца своей сессии. Если пароль утёк,
  смените его и перезапустите Gateway: все выданные права сразу перестанут действовать. Хранить вместо
  пароля его хеш можно позже, интерфейс при этом не изменится.
- Права по паролю действуют только в той сессии, где пароль введён; в другом браузере его нужно ввести
  снова.
- Состав администраторов из списка меняется только перезапуском Gateway с новым `ADMIN_YANDEX_IDS`.
- Админ определяется учётной записью Яндекса: без входа через Яндекс прав администратора нет ни по списку, ни по
  паролю.
- Журнал записывает отказы в доступе, вход по паролю с его снятием действия с пакетами оценки и обновления списка репозиториев. Действия
  пользователей (вход, запуск анализа) добавляются следующими этапами.
- Время пакета в пробном расчёте приблизительное: оно берётся из среднего времени недавно оценённых репозиториев
  пакетов, а пока их нет — 90 секунд на репозиторий. Настоящее время зависит от размера репозиториев и очереди grade-service.
