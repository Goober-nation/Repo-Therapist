# Repo Therapist

Стенд: [repo-therapist.alo.quest](https://repo-therapist.alo.quest)

Сервис оценивает открытые репозитории SourceCraft по шкале 0–100 в шести категориях и объясняет,
из чего сложилась оценка. Он также формирует приоритизированные рекомендации и позволяет
пользователю, вошедшему через Яндекс ID, проанализировать собственные (в том числе приватные)
репозитории.

Разработан в рамках кейса Yandex Cloud «SourceCraft Repo Health».

## Возможности

| Требование (ТЗ) | Статус |
|---|---|
| Оценка здоровья по шести категориям, Score 0–100 с детализацией по категориям | ✅ |
| Объяснение и рекомендации | ✅ |
| Рейтинг открытых репозиториев | ✅ |
| Анализ собственного репозитория после входа через Яндекс ID | ✅ |
| Периодический пересчёт | ✅ |
| Выгрузка отчёта (Markdown / PDF) | ✅ |
| ★ Защита рейтинга от накрутки | ✅ |
| ★ AI-summary и рекомендации | ✅ |

## Архитектура

| Сервис | Роль |
|---|---|
| `gateway-service` | HTTP API для фронтенда, авторизация через Яндекс ID |
| `aggregator-service` | Оркестрирует задачи оценки, единственный сервис с доступом к БД на запись, управляет `repo_lock` |
| `repository-service` | Клонирует репозитории и выгружает дерево файлов, git-историю, issues и milestones в S3 |
| `grade-service` | Считает оценки категорий по выгрузкам из S3 |
| `llm-service` | Оценка документации и AI-summary (Python, модель Яндекса) |
| `security-wrapper-service` | Читает результаты AppSec SourceCraft (SAST/SCA/секреты) |
| `sourcecraft-wrapper-service` | gRPC-обёртка над REST API SourceCraft |
| `rating-service` | Публичный рейтинг, только чтение |

Контракты сообщений: [docs/kafka-contracts.md](docs/kafka-contracts.md). Схема БД:
[docs/schema.sql](docs/schema.sql). RPC обёрток: [docs/api_docs.md](docs/api_docs.md).

## Быстрый старт

Требуется: Docker и Docker Compose, Go (версия из `go.work`) и персональный токен доступа
SourceCraft.

```bash
cp .env.example .env        # заполните SOURCECRAFT_PAT, S3_*, POSTGRES_*
docker compose up -d        # Postgres, S3 (RustFS), Redis, Kafka, миграции, сервисы, фронтенд
```

- Фронтенд: http://localhost:8081 (рейтинг — `/`, анализ — `/repo/<org>/<repo>`,
  собственные репозитории — `/my`). Подробнее: [frontend/README.md](frontend/README.md).
- Консоль S3 (RustFS): http://localhost:8055/rustfs/console/index.html

Все настройки описаны в комментариях в [.env.example](.env.example).
Ручное сквозное тестирование: [docs/testing.md](docs/testing.md).

```bash
go build ./... && go test ./... && go vet ./...
```

## Repo Health Score

Каждая категория оценивается от 0 до 100. Итоговая оценка — взвешенное среднее категорий,
по которым есть данные:

| Категория | Вес | Режим |
|---|---|---|
| Активность | 20% | публичный + приватный |
| Issues | 20% | публичный + приватный |
| Документация | 15% | публичный + приватный |
| Состояние кода | 10% | публичный + приватный |
| Security | 20% | только приватный |
| CI/CD | 15% | только приватный |

- **Публичная** оценка (без токена пользователя) использует 4 категории, веса нормируются к 100.
- **Приватная** оценка (с токеном пользователя) использует все 6. Открытые уязвимости
  ограничивают итог.
- Почему Security и CI/CD только в приватном режиме: доступ платформы. Данные AppSec и
  `cicd/runs` требуют токена владельца. ТЗ (§3.2) допускает исключение категории, если причина
  описана.

Полная методика, включая причины отличия весов от примера в ТЗ:
[docs/grading/00-overview.md](docs/grading/00-overview.md).
Метрики каждой категории и пошаговый расчёт — в [docs/grading/](docs/grading/):
[активность](docs/grading/activity.md) · [issues](docs/grading/issues.md) ·
[security](docs/grading/security.md) · [документация](docs/grading/documentation.md) ·
[CI/CD](docs/grading/ci-cd.md) · [состояние кода](docs/grading/code-health.md).

### Отсутствие данных

«Нет данных» не считается плохим результатом (в большинстве случаев). Категория без данных
помечается **«Нет данных»** и исключается, веса остальных категорий нормируются заново.

Исключение — категории CI/CD и Документация. Командой решено ставить им низкую оценку, если в
репозитории нет соответствующей информации: отсутствие документации или пайплайна — признак
нездорового репозитория.

## Рекомендации

Рекомендации формируются в два этапа:

1. **Правила.** Каждая метрика ниже здорового порога даёт рекомендацию из
   [config/recommendations.yaml](config/recommendations.yaml) с приоритетом `high`/`medium`/`low`.
   Рекомендации по документации формируются детерминированно на основе вычетов, на русском языке.
2. **AI.** LLM-сервис получает итоговую оценку, оценки категорий и рекомендации из шага 1 и
   формирует summary, сильные и слабые стороны и список рекомендаций с приоритетом
   (HIGH/MEDIUM/LOW). Модель опирается на переданные факты и не пересчитывает оценку.

## Защита от накрутки ★

Публичный рейтинг защищён от накрутки лайков, пустых коммитов и искусственной активности:

- **Лайки не влияют на оценку.** Рейтинг SourceCraft (лайки) отображается и доступен как
  дополнительная сортировка, но никогда не участвует в расчёте. По умолчанию рейтинг
  сортируется по Repo Health Score.
- **Пустые коммиты, коммиты ботов и коммиты с датой в будущем отбрасываются** до расчёта
  активности.
- **Фиктивный CI получает 0.** Пайплайн, выполняющий только команды вроде `echo`, `true` или
  `sleep`, не считается CI.
- **Уязвимости ограничивают оценку.** Открытые critical-находки AppSec ограничивают приватную
  оценку значением 59, открытые high — значением 79.

Известное ограничение: почти пустой репозиторий всё ещё может получить высокую оценку;
запланирован флаг низкой достоверности.
Подробнее: [docs/grading/00-overview.md#anti-manipulation-2026-09-28](docs/grading/00-overview.md#anti-manipulation-2026-09-28).

## Использование AI и внешних сервисов

- LLM-сервис оценивает документацию по алгоритмически выбранным фрагментам: 8 разделов до
  30 строк каждый, контекст не более 32 КБ. Модель видит только выборку и не может сообщать о
  недостатках в непросмотренных частях. Проверяется только формат ответа.
- LLM-сервис также формирует summary репозитория, отображаемое на странице.
- AI не используется для расчёта категорий Активность, Issues, CI/CD, Security и Состояние кода.

## Масштабирование

Система спроектирована с расчётом на горизонтальное масштабирование (сейчас каждый сервис
работает в одном экземпляре):

- Сервисы общаются асинхронно через Kafka; у каждого обработчика (repository, grade, llm) своя
  consumer group.
- Сервисы-обработчики не хранят состояние: данные репозитория лежат в S3 (RustFS), результаты — в
  Postgres, куда пишет только агрегатор.
- Таблица `repo_lock` не даёт запустить две оценки одного репозитория одновременно.
  Если сервис упал посреди оценки, блокировка снимается по сообщению о сбое, а без него — через
  `GRADING_LOCK_TIMEOUT` (20 минут); пользователь видит «оценка прервана» и может запустить её снова.
- Новых оценок по запросам пользователей — не больше `GRADING_REQUEST_LIMIT` (10) за
  `GRADING_REQUEST_WINDOW` (10 минут) на весь сервис; сверх лимита отдаётся прошлая оценка или
  429 с `Retry-After`. Плановый пересчёт в лимит не входит.
- Клонирование идёт в `/dev/shm`, при нехватке места — на диск; `CLONE_TIMEOUT` и `GRADE_TIMEOUT`
  ограничивают время на один репозиторий.
- Периодический пересчёт (`GRADING_REGRADE_INTERVAL`) можно ограничить топом N репозиториев
  (`GRADING_REGRADE_LIMIT`).
- Запросы к SourceCraft и AppSec повторяются при ответах 429/5xx и сетевых ошибках.

## Ограничения

- Список публичных репозиториев берётся из API SourceCraft (`GET /repos`, на 2026-09-28 —
  около 28 500 репозиториев). Сейчас обходится не более `SOURCECRAFT_MAX_PAGES` страниц
  (по умолчанию 50 × 20 = до 1000 репозиториев). Анализ собственного репозитория принимает slug
  или URL от пользователя.
- Security и CI/CD доступны только владельцам репозитория.
- Документация оценивается по выборке, а не целиком.
- `SOURCECRAFT_MAX_PAGES` ограничивает историю issues у очень крупных репозиториев.
