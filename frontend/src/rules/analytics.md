# Углублённая аналитика (справочные показатели)

Статус: этап A (2026-10-04) — фактор автобуса и карта владельцев кода. Этап B (ревью-аналитика
pull request и аналитика задач: время первого ответа и обработки) запланирован и описан в конце.

## Что измеряется

Два показателя о том, кто делает работу в репозитории:

- **Фактор автобуса** — наименьшее число авторов, которые вместе сделали не меньше половины
  коммитов за период. 1 значит, что проект держится на одном человеке.
- **Карта владельцев** — для каждого каталога верхнего уровня: кто больше всех менял его код, какую
  долю изменений он сделал и сколько авторов внесли заметный вклад; плюс сравнение с файлом
  CODEOWNERS, если он есть.

**Эти показатели справочные и не входят в Repo Health Score.** Они не имеют веса, не меняют оценку,
категории и порядок в рейтинге, и «нет данных» по ним никогда не считается плохим результатом.

## Как считается, простыми словами

1. Берутся коммиты, которые Grade service уже прочитал для Активности, за последние
   `analytics.window_days` дней (180), **после тех же фильтров**: пустые, ботовые, датированные
   будущим и мелкие (меньше 4 строк) коммиты отбрасываются, так что мусорные коммиты не создают
   «команду» на бумаге.
2. Если учтённых коммитов меньше `analytics.min_commits` (5), оба показателя — «нет данных»:
   вывод о распределении работы по трём коммитам был бы выдумкой. Если коммиты вообще не удалось
   прочитать, то же самое.
3. Автор определяется по email без учёта регистра; показывается имя, под которым он чаще всего
   коммитит. **Email наружу не отдаётся никогда.**
4. **Фактор автобуса.** Авторы сортируются по числу коммитов; к самому активному добавляются
   следующие, пока набранная сумма не достигнет половины всех коммитов. Сколько авторов
   понадобилось — это и есть фактор. Рядом показываются до `analytics.top_authors` (5) самых
   активных авторов с долей коммитов.
5. **Карта владельцев.** Каждое изменение файла относится к каталогу первого уровня (файлы в
   корне — к «(корень)»). Вклад автора в каталог — сумма добавленных и удалённых строк по всем его
   коммитам; изменение бинарного файла считается одной строкой. Для каждого каталога берётся
   автор с наибольшим вкладом (основной владелец) и его доля; «владельцами» считаются все, у кого
   доля не меньше 10%. Показываются `analytics.top_areas` (8) самых изменяемых каталогов.
6. **CODEOWNERS.** Ищется файл `CODEOWNERS`, `.github/CODEOWNERS` или `docs/CODEOWNERS`. Для
   каждого файла, изменённого за период, берётся последнее подходящее правило (как в Git-платформах);
   файл считается закреплённым, если у этого правила указан владелец. Показывается доля
   закреплённых файлов и число правил.

## Формат

Поле `analytics` в сообщении `grading.results` (см. `docs/kafka-contracts.md`) и ответ
`GET /analytics/{org}/{repo}` (см. `docs/api_docs.md`):

```json
{
  "version": 1,
  "window_days": 180,
  "bus_factor": {
    "status": "ok", "value": 2, "commits": 120, "authors": 5,
    "top_authors": [{"name": "Ann", "commits": 70, "share": 0.58}]
  },
  "ownership": {
    "status": "ok",
    "areas": [{"path": "src/", "files": 40, "lines": 5200, "top_owner": "Ann", "top_owner_share": 0.8, "owners": 2}],
    "codeowners": {"present": true, "path": "CODEOWNERS", "rules": 4, "covered_share": 0.9}
  }
}
```

`status` блока — `ok` или `no_data`; при `no_data` числа не нужно показывать (`value` опускается,
списки пусты). `covered_share` равен `null`, если файла нет или за период нет изменённых файлов.

## Нет данных vs. настоящий ноль

- Мало коммитов за период или коммиты не прочитаны — `no_data`, а не «фактор 1».
- Файл CODEOWNERS не найден — это факт (`present: false`), а не плохая оценка; карта владельцев от
  него не зависит.
- Аналитика считается для публичной и приватной оценки отдельно и хранится в разных таблицах
  (`repo_analytics_public`, `repo_analytics_private`); приватную видит только владелец.
- Репозиторий, оценённый до появления аналитики, возвращает статус `NO_DATA` до следующей оценки.

## Когда аналитика пересчитывается

Обычно оценка пересчитывается, только если в репозитории была активность после последней оценки.
Для аналитики добавлена вторая проверка: если у репозитория есть оценка, но нет строки аналитики
(например, он оценивался до появления этого блока), агрегатор считает оценку устаревшей и запускает
повторную оценку, даже если репозиторий не менялся. Проверка включена по умолчанию и отключается
переменной `ANALYTICS_REGRADE_MISSING=false` у aggregator-service; отключать её нужно, если в
`config/grading.yaml` стоит `analytics.enabled: false`, иначе каждый запрос запускал бы новую оценку.

## Известные ограничения

- Автор определяется по email: один человек с двумя адресами считается двумя авторами (фактор
  завышается), а общий адрес нескольких людей — одним. Слияние через squash или ребейз приписывает
  работу тому, кто выполнил слияние.
- История ограничена окном клонирования (365 дней) и `window_days`; для спящего проекта данных
  может не хватить, и это честное «нет данных».
- Фактор автобуса не отличает владельца от случайного участника: считаются коммиты, а не важность
  изменений. Поэтому он справочный.
- Сопоставление CODEOWNERS упрощённое: поддерживаются `*`, `**`, `?`, привязка к корню и каталоги,
  но не классы символов и отрицание `!`; имена владельцев не проверяются и не сопоставляются с
  git-авторами, поэтому «владелец по CODEOWNERS ≠ реальный автор» не вычисляется. Доля закрепления
  считается по файлам, изменённым за период, а не по всему дереву.
- Показатели можно «улучшить» накруткой коммитов от нескольких адресов; поэтому они не входят в
  оценку, а мелкие и пустые коммиты отфильтрованы (см. `00-overview.md`, «Устойчивость к накрутке»).

## Этап B (запланировано, не реализовано)

Ревью-аналитика pull request (время до первого ревью и до слияния, доля PR без ревью,
концентрация ревьюеров) и аналитика задач (время до первого ответа, разброс времени закрытия).
Данные для них — PR, ревьюеры и комментарии SourceCraft через обёртку (новые RPC) и выгрузку в S3.
Для таймингов будет действовать защита от импорта: если 80% и более PR или задач созданы в один
день, тайминги — «нет данных» (измерено: у зеркал с GitHub 96–100% PR созданы в день импорта).
Выгрузка ограничена последними 10 PR и 25 задачами (настраивается).
